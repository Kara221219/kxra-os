# Transactional email staging activation

This playbook activates one controlled non-production sender after core staging passes. It does not authorize real customer or partner contact.

1. Verify a dedicated sending subdomain in Resend. Keep the root domain and public marketing project free of provider credentials.
2. Choose the exact `KXRA_EMAIL_FROM` value and one owner-controlled staging recipient. Approve all nine rendered templates before sending.
3. From a clean pushed phase-branch checkout, run `staging:email-role:plan`, provide a generated 48–128-character `KXRA_STAGING_EMAIL_WORKER_PASSWORD` without echo, set `KXRA_STAGING_EMAIL_WORKER_ROLE_CONFIRMATION=EMAIL-ROLE:<project-ref>:codex/phase-2-completion`, then run `staging:email-role:apply` and `staging:email-role:verify`. The guarded operator creates `kxra_email_runner`, which may assume only the no-login/no-bypass `kxra_email_worker` role. It rejects ownership, direct grants, admin-option membership and privileged attributes.
4. Generate a 32-byte random encryption key, encode it as base64url and store it as `KXRA_EMAIL_SECRET_KEY` in the private OS and worker secret stores only.
5. Create a separate Vercel Preview project rooted at `apps/email-worker`; do not attach Resend to the OS or marketing projects. Store `KXRA_EMAIL_WORKER_DATABASE_URL`, `RESEND_API_KEY`, `KXRA_EMAIL_FROM`, `KXRA_EMAIL_SECRET_KEY` and a separate 64–128-character `KXRA_EMAIL_WORKER_TRIGGER_SECRET` only in that worker. The worker database URL must use `kxra_email_runner`, TLS `verify-full` and the shared-pooler role/project username form when applicable. Store the same encryption key plus `RESEND_WEBHOOK_SECRET` in the private OS server environment. Never add any email value to marketing or a client variable.
6. Register `https://<private-staging-origin>/api/webhooks/resend` for delivered, delivery-delayed, bounced, complained, failed and suppressed email events.
7. Keep the core OS profile at `KXRA_EMAIL_ENABLED=false`. For the controlled provider slice, set `KXRA_STAGING_CAPABILITY_PROFILE=transactional-email` in the OS and worker, enable email in those two projects only and run each project's staging preflight before deployment. The OS profile may hold only encryption/webhook custody; the worker profile may hold only delivery custody.
8. Invoke the worker with an empty `POST /api/process` and `Authorization: Bearer <KXRA_EMAIL_WORKER_TRIGGER_SECRET>`. Anonymous, malformed and body-bearing requests must fail before a database claim. Trigger.dev remains the target scheduler; do not enable a schedule until replay, cancellation, secret rotation and delivery-time revocation pass staging.
9. Use **Resend with new link** on the controlled pending invitation, then invoke the worker once. Verify ciphertext exists without plaintext token, one provider request uses the outbox operation key, provider acceptance records `SENT`, and the signed event records `DELIVERED`.
10. Exercise invalid trigger secret/body, invalid webhook signature, replay, expiry, revocation-before-send, 429 retry, permanent failure and uncertain transport. Uncertain transport must remain `RECONCILIATION_REQUIRED` with no automatic resend.
11. Rotate the trigger and webhook secrets and prove both provider-documented webhook transition signatures during the rotation window. To rotate the encryption key, first cancel or drain every queued secret and issue fresh links.

Record commit, environment, sender domain, controlled recipient owner, provider message/event IDs, timestamps and redacted results in acceptance evidence. Delete the synthetic account after the retention check. Leave real invitations disabled pending legal copy and owner approval.
