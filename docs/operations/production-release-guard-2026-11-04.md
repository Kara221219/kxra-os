# Hosted release guard

Local implementation based on accepted `9e2fe569b3817652850987c8114adc14e00b9875`. No hosted access or mutation, real credentials, provider request, deployment, payment or spending is part of this work.

`npm run release:check` is offline and needs no configuration or credentials. It intentionally exits1/BLOCKED on this integration checkout because0118/0119 are fixture migrations. It never filters them out or treats passing local119 tests as release authority. The output identifies the blocked file without SQL or secrets. Exit0 means only SOURCE_ELIGIBLE_FOR_REVIEW, with authorization:false.

The separate `packages/release/hosted-schema-policy-v1.json` pins all117 production-review-baseline filenames and raw SQL hashes, an expected117/214/207 database profile, and the exact known fixture namespace/relation/function registry. These counts are not a claim that a hosted target is empty, current, approved or initialized. Policy updates require a reviewed source change; there is no environment bypass. Generic `migrationManifest` and the local119 cohort are unchanged.

Staging/production migration operators, staging canonical seeding and production bootstrap all call the hosted source guard before target configuration, repository checks or database construction/connection. Unknown, renamed, copied, changed, missing or nonregular/symlinked migration sources fail. Any declared extension fails; unnumbered fixture proposals are not promoted. Validated migration SQL stays in memory and is the SQL subsequently executed. Existing branch/pushed-head/exact-SHA, target, verified TLS, confirmations, unknown ledger/hash history and production-empty-initialization restrictions remain. This patch does not repair or authorize that historical initialization-only operator for an existing production target.

After connection, a read-only catalogue check refuses the two known fixture namespaces, all24 known fixture relation names (every pg_class kind, including views/sequences), and all23 fixture function names (any signature). It also runs during verification and inside each apply advisory lock before the first write. An empty fixture schema or a partial extension still blocks. These checks are additional to existing ledger, counts, ACL and unknown-object checks; they are not a substitute for complete target reconciliation and do not classify every possible renamed/manual SQL object. Manual privileged SQL or a different external deployment tool is outside this operator boundary.

`npm run test:release-guard-native` requires a clean committed source and the existing exclusive native lease. It clones the exact head into an owned short path, verifies the pinned hashes before removing only fixture0118/0119 in that disposable clone, then starts a local Unix-socket117 database. It measures the117/214/207 baseline and probes every known fixture namespace/relation/function marker in rollback-only transactions, including relation markers represented as views and functions with different signatures. Baseline state must return after every probe. The owned cluster is stopped and its lease released only after status3/no PID confirmation. It never edits this checkout or a source/frozen worktree. This cohort is test materialization, not a hosted release candidate or upgrade authorization.

Focused tests also cover copied/renamed fixture SQL, altered/missing source, file/directory symlinks, extension declarations, exact fixture-registry/hash completeness and all12 hosted command entrypoints with network tripwires. Existing migration/seed/bootstrap tests are retained. Native and final exact-source regression evidence is recorded in the enclosing workspace's `acceptance-evidence/production-release-guard-acceptance.json`; execution is pending at this source checkpoint.

A future production candidate must explicitly exclude fixture migrations/extensions, retain reviewed production behavior, supply a newly reviewed exact manifest and reconcile its target ledger/inventory/roles/backups before any action. Future genuine production migrations intentionally fail this frozen baseline until their source/policy update is reviewed. Do not renumber committed fixture history, lower inventory counts to force a match, or assume removal of two files in a test clone makes an integration release deployable.
