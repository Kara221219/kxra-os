# Custom-app local lifecycle — 3 November 2026

This branch adds a working **synthetic local declarative form lifecycle**, not Kylon parity or hosted app publishing. It is based on release commit `43e3906859b58e69370a1069a44e6dc1cefc6d03`, in the independent checkout `/Users/kara/Documents/Codex/2026-11-03/task-3/custom-apps`, branch `codex/custom-app-local-lifecycle`. The frozen release checkout is not modified.

## Try it

From this checkout, run `npm run dev:custom-apps`. This uses the existing guarded local fixture launcher and installs the extension into this checkout's local synthetic PostgreSQL cluster. Sign in as a fixture user, create/open a room, and choose **Local custom apps**. The room creator can register a JSON schema, preview, register another immutable version, publish locally and roll back to a previous local release. Other authorized room members can inspect and preview. There is no external publication endpoint.

Run `npm run test:custom-apps` for a fresh disposable database, loopback Next server, unit/HTTP/SQL tests, Chromium security/lifecycle tests, and migration/RLS verification. Its private logs and disposable datasets are under `.runtime/apps-*`; PostgreSQL and the application stop when verification finishes. No real accounts, provider keys or remote credentials are needed. `DATABASE_URL`, hosted auth and Vercel environments are rejected.

## Contract and boundaries

- `kxra.form.v1` supports text, textarea, checkbox and select fields only. The schema has a title, description and 1–20 uniquely keyed fields, with at most 20 options per select. Unknown fields, custom code, expressions, URLs and capability bindings are rejected. The HTTP input is capped at 32 KiB; SQL independently validates schema shape and size. Rooms have at most 20 apps, with at most 100 immutable versions per app.
- PostgreSQL is authoritative. Requests use the existing verified actor and scoped authenticated transactions. Both org/project/room access and active private-room membership are checked by existing helpers. Only the room creator with write access can register or release. Client-supplied identities and roles are rejected. Local mode and fixture identity are mandatory; SQL denies absent/hosted execution mode.
- The schema and runtime format form an immutable JSON artifact. A stored SHA-256 is checked against PostgreSQL's canonical artifact JSON text encoded as UTF-8. Versions and release events reject updates/deletes, and clients have no direct write grants. The runtime format must be bumped for future incompatible renderer changes. This is database immutability against application roles, not protection against an administrator replacing SQL or restoring a database.
- Registration appends a version. Local publication changes only an app's active-version pointer and appends a release event. Rollback requires a previously released version of that same app. App/room binding, row locking and expected revisions prevent cross-app pointers and stale/concurrent overwrites. Metadata, versions and recent release history are returned from one database snapshot. History responses show the latest 100 events; rollback eligibility uses all history.
- A trusted renderer escapes all labels/options. Preview is a `srcDoc` iframe with an empty `sandbox`, opaque origin and no-referrer policy. Its CSP denies scripts, network, images, nested frames, workers, objects, base URLs and form submission. Native form controls and reset work; entries are transient and cannot read parent DOM or localStorage. No uploaded source executes, and no filesystem/network/secrets/provider capability is exposed to app definitions.
- The installer confines the real runtime under this checkout's `.runtime`, rejects redirected socket directories, and verifies the connected PostgreSQL data directory before executing the fixture extension as the local OS administrator. Tests cover foreign runtime paths, socket-directory symlinks and socket-file redirection.

`packages/custom-apps/local-schema.sql` is deliberately an **unnumbered local fixture extension**. It is not in `supabase/migrations`, does not change the release migration ledger, and must never be applied to staging or production. The release owner retains migration allocation and hosted activation. The Supabase CLI is unavailable here; this implementation follows the repository's existing `pg` fixture runner instead of claiming CLI/advisor verification.

## Review and evidence

An independent code/security agent reviewed implementation and then the installer/tests. Findings fixed: SQL NULL execution-mode fail-open; inconsistent multi-query detail snapshots; rollback labels inferred from truncated history; installer target containment (including foreign working directories); and sparse-array validation for direct JavaScript inputs. Final review reported no remaining high or medium findings. PostgreSQL also rejected the initial generated digest expression because `convert_to` is not immutable; digest insertion plus a database CHECK now validates the same canonical bytes. A test fixture originally attempted an unauthenticated administrative membership update and was corrected to use the authorized room-membership function. These failures are not represented as passing runs.

Focused final native run: **8/8 tests passed**, including malformed schemas at HTTP and SQL boundaries, missing/hosted-mode denial, anonymous/non-manager/hidden-room denial, cross-app/room denial, immediate membership revocation, immutable rows/digests/history, stale and concurrent revisions, rollback invariants, resource limits, installer containment and a real Chromium lifecycle. Migration/RLS verification passed with **117 release migrations and 217 protected tables** (including the three local extension tables). Log: `.runtime/custom-apps-isolated-final.log`. The extension integration suite lives under `tests/custom-apps/` and is intentionally run only by its own harness, so it cannot install extra tables into the canonical release-schema suite. The two pure unit tests also run in the ordinary root suite; counts overlap and must not be summed.

## Remaining product gaps

No arbitrary-code runtime, generated source build, AI app generation, persisted app submissions, data bindings/actions, app-specific sharing policy, external hosting/domain/URL publication, hosted migrations/entitlements, rollback of application data, release approvals, archive/delete UX or full Kylon parity is implemented. Publication/rollback retries are revision-conflicted rather than idempotency-key replayed; reload after an ambiguous network outcome. Local release history is append-only and currently has no total event quota. This slice must not be marketed as a working general app builder or a launch-ready hosted feature.
