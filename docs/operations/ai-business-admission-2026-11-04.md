## Binding and enforcement

The existing0115 `business_current_review` remains authoritative for the current declaration, policy, customer, execution scope, offer/mapping, terms and legal/payment/provider/tax review. Billing RPC signatures and paid-work authority remain unchanged. A free-text declared provider is only an additional consistency check, normalized by trim/uppercase; it is never the typed provider/model authorization by itself.

A first real connection submission creates an immutable private intent under the verified current app principal and MFA-owner authority. It records server-generated connection ID, org/actor/session, typed provider, exact model, endpoint alias, full resolved-endpoint digest, per-intent credential fingerprint and the current business-review ID. No plaintext key or encrypted provider key is stored in the intent. The existing HTTPS API request still transiently receives the user-entered key to calculate that private fingerprint; this is not a key-free request protocol. The fingerprint is SHA-256 over a domain prefix, random connection ID and supplied key, is private sensitive metadata rather than authentication authority, and is never returned to the customer or put into provider requests.

Missing business review can register a finite pending intent but cannot become eligible through a later implicit rebind. A fresh intent is required once the necessary business review exists. An opaque connection reference is returned in a finite409 error; there is no automatic clearance, country allowlist, model substitution or funded fallback.

Only a separately authorized owner/operator evidence process can append a private AI connection review. It must bind that exact intent to account-reference and provider-evidence hashes, reviewer reference, validity window and account mode. All four private tables have RLS and no direct client/worker privileges. Customer input cannot set org/actor/review/state, and cannot self-approve. Hashes are references to evidence, not proof of its correctness or a live provider-account attestation. The latest review alone may authorize; blocked, unknown, expired or withdrawn successors never fall back to older clearance. Google requires independently reviewed `GOOGLE_PAID`; other supported providers require `CUSTOMER_BILLED`. An unsupported declaration/provider combination remains closed.

An eligible resubmission must include `admission_id` and exactly the same provider/model/endpoint/key. The shared `sealAdmittedAiConnection` helper calls the vault only after exact current server-owned admission. Missing RPC, malformed/mismatched receipt and missing/blocked/review-required authority cannot call the vault. The database rechecks current review before saving and binds the stored ciphertext digest to that review. The old real connection-save RPC cannot bypass admission; renamed core functions are owner-only. Credential generation is represented by the immutable connection ID, private fingerprint and stored ciphertext digest; no mutable browser-owned version grants authority. SQL trusts the application backend to seal the same plaintext whose fingerprint it computed; SQL cannot decrypt or prove plaintext/ciphertext correspondence. There is no new real-key importer or vault implementation.

The 24-hour intent TTL applies only to initial activation. It does not impose a 24-hour lifetime on an already saved connection. Saved authority is governed by the current business/AI review, session, connection generation and existing paid/access checks. Enabling a real connection requires current review and exact active caller/JWT session. Disabling after review withdrawal remains allowed to the valid current owner. Old JWTs cannot re-enable a new-session connection.

`team_connection_active` now requires current exact AI authority for real providers. Existing run/context/memory, queued-job, execution-grant and publication checks retain their original gates and incorporate that predicate. Every new run stores an immutable original connection/generation snapshot; real runs additionally pin the exact review. Publication rechecks that original snapshot. An agent rebound to another eligible real connection or to FIXTURE cannot change the original authority or select an exemption, and releases no output. Ordinary original fixture completion remains supported only under its explicit fixture guard. Legacy RUNNING rows without a snapshot fail closed; release must drain or cancel them before promotion rather than fabricate admission history. `ai_run_admission` additionally checks current caller session, original run/agent connection, ciphertext generation and actual endpoint digest. A changed declaration, business policy/review, model, endpoint, credential, session or agent binding cannot reuse the run's prior authority.

The actual app execution path supplies this run-bound check to `generate`. It runs before `openKey`; secure transport requires a guard, checks it before DNS and again after the public-address lookup immediately before opening the provider request. The callback binds the actual target URL and rejects changed endpoint configuration. There is no automatic retry/regrant after denial. These are local fences, not distributed atomic revocation: a provider request already accepted cannot be recalled by later withdrawal, and an already decrypted key cannot be made retroactively unread. Existing cancellation/uncertain-outcome/receipt controls remain in force.

The only fixture exemption is the existing fixed FIXTURE provider/model/key under explicit verified fixture execution mode. A fixture-looking real provider, hosted FIXTURE request or real old-save RPC cannot use it. Existing default-off external-provider and hosted-job controls remain unchanged.
