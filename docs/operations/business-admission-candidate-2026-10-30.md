## Decision and payment fences

States are `ELIGIBLE`, `BLOCKED`, `REVIEW_REQUIRED`. A country code is only an ISO location identifier, never automatic eligibility or a sanctions list. All 249 ISO identifiers are accepted for application. No country is presumed cleared. Missing or expired policy/review, unresolved legal/payment/provider/tax review, changed declaration/provider, mismatched scope/customer/offer/mapping/terms/tax evidence or withdrawn decision fails closed. A newer unresolved/blocked review never falls back to older clearance.

A qualified reviewed decision pins declaration ID (therefore business location, provider and declarations), org, actual Stripe customer, immutable execution scope, offer/mapping revision, exact terms document/version/hash and mapping tax-review hash. Each legal/payment/provider/tax dimension requires a status and opaque source-evidence hash; the policy has a reviewed owner reference and validity window. These hashes must resolve to actual reviewed evidence in the existing approved evidence process; a hash alone does not establish correctness. Only all four `CLEARED` values yield `ELIGIBLE`. One `BLOCKED` dimension yields `BLOCKED`; everything else needs review. Saved/unvalidated tax IDs are not clearance and no tax API is activated.

A trigger resolves the server decision on CHECKOUT insertion and stores its immutable review ID on the intent, independent of any client-supplied ID. A request replay must still have current eligibility. Claim transition, existing worker current-state fence, read-only dispatch presentation and completed checkout result/URL recovery all recheck it. Wrappers preserve the original mode, MFA, legal, binding/ledger and policy guards. Old renamed core functions are owner-only. PORTAL and historical paid-proof refresh remain on existing behavior; this does not revoke previously paid access wholesale. The current Stripe customer reservation may still occur before a reviewed checkout; it cannot collect payment. No automatic checkout is created for a blocked/review-required applicant.

Revocation before an existing worker's final pre-POST fence prevents its provider request. A provider request/session already accepted cannot be undone by local withdrawal: cancellation/expiry and reconciliation of an already issued checkout remain existing operator responsibilities. This candidate does not claim distributed atomic revocation across Stripe HTTP.
