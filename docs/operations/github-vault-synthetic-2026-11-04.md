## Implemented boundary

`packages/connectors/github-vault-synthetic.ts` supplies an opt-in credential broker to the existing `LocalGithubAdapter`. The transport still accepts only an explicit loopback HTTP fake endpoint and the literal fixture token. It derives paths from the fixed typed account/repository/issue binding, validates provider evidence, denies redirects and refuses real provider origins. No production API route imports either new module.

A one-use five-minute challenge attests a **synthetic** installation observation: tenant, user, session/grant versions, account, installation, selected repository, issue identity (not a pull request), author, app/client identity and read/write permissions. The SQL confirmation compares the entire expected proof; the observer performs no provider IO. This is a contract and negative-test seam for future server-observed provider identities, not evidence that GitHub authenticated any identity.

A generated in-memory 32-byte fixture key seals only the literal fake token using AES-256-GCM. Authenticated data binds purpose, tenant, user, connection, credential reference, grant/session versions, provider target, scope and lease expiry. PostgreSQL persists the envelope, never its plaintext or encryption key. Resolving a lease rechecks active membership/account/session, exact grant/reference/binding/scope and expiry. Missing leases, key loss, tampering, rotation, revocation and expiry fail closed. Provisioning never silently overwrites a lease; there is no token mint/refresh/regrant fallback. The cipher destroys its own key buffer on disposal. This is not a managed vault, KMS, hardware custody or real token refresh implementation.

`packages/connectors/github-receipt-synthetic.ts` wraps an explicitly supplied trusted scope. The approved one-use claim atomically stores a hash of a fresh 256-bit receipt token, bound to one write, attempt and approved digest. The raw token stays in the worker closure; it is not returned in customer results, SQL rows, logs or files. The worker allows at most 100 unresolved in-memory permits. Missing/mismatched permits cannot fall back to normal outcome publication. Ordinary reconciliation still needs the original current identity and remains read-only.

The separate `kxra_github_receipt.publish` function accepts only that receipt token, attempt, digest and bounded outcome evidence. It records historical outcomes even after membership, account, session and connection withdrawal, returning only `{recorded,state}`. It cannot list tenant data, resolve credentials, approve, claim, dispatch, read a provider or grant reconciliation authority. The approved JSON payload digest is recomputed after locking, and exact accepted-body hash, author, issue URL and positive safe comment identity are checked against immutable approval; the existing provider-comment uniqueness constraint is retained. Permits expire after 24 hours, can be revoked, and allow at most eight new observations. Exact duplicate receipts are idempotent; conflicting terminal receipts cannot regress outcomes. Receipt validity is rechecked after lock acquisition.

An uncertain write stays uncertain; the receipt cannot turn uncertainty into definite rejection/nonexecution. A lost in-memory receipt token or worker restart does not authorize a new send or a new claim. Recovery requires separately authorized provider-read reconciliation when the customer still has authority, or a future narrowly scoped operational reconciliation design after withdrawal. The new slice does not add crash-surviving token custody.

Both new vault and receipted-claim RPCs explicitly compare caller JWT session version with current account authority. Existing connector routes/RPCs remain unchanged and continue to require their existing verified server session boundary; the legacy list RPC is not made into a standalone session verifier by this proposal.
