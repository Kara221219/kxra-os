# Incremental application126 operator

This is an additive local implementation, not a hosted deployment or release approval. The existing `production-migrations.mjs`, its core, the hosted117 policy, all application SQL payloads, historical manifests and application cohort metadata are unchanged. In particular, the cohort's historical `hostedExecutorImplemented: false` describes that artifact when written, not permission to run this separate command.

## Interface and scope

Run `node scripts/production-application.mjs plan|apply|verify` from clean committed source. There is no initialization, down migration, fixture conversion, role creation, Auth-provider configuration, backfill, feature activation, external fencing-database installation, payment or provider call. Only exact existing117 through126 application ledger prefixes are accepted. The real table is `public.kxra_schema_migrations(name, sha256, source_commit)`; migration SQL and its ledger entry commit together. No separate version/digest ledger is substituted.

All three commands require the existing production target environment (`KXRA_ENVIRONMENT`, project reference, exact source commit, direct migrator URL and CA certificate). The only accepted endpoint is `db.lhbgeucifxxcdoyrnesf.supabase.co:5432`, database/user `postgres`, with full TLS chain and hostname validation. The server's current and session users must both be `postgres`, and recovery replicas are refused. A present `app.settings.project_ref` must match; its absence is permitted and never repaired or fabricated. Session poolers are deliberately unsupported by this additive command.

`plan` and `verify` use a read-only repeatable-read transaction. Plan returns pending exact names/hashes, source and ledger digests, finite Auth column/role/trigger metadata, a source-derived application catalogue match, actual server version and hashes of observed Auth metadata. It reads no Auth user/session rows or application business payloads. Raw database errors and connection URLs are never printed. An unsupported structural Auth precondition fails closed with a sanitized error; a managed-schema mismatch returns `TARGET_CATALOG_REVIEW_REQUIRED` with hashes and no apply eligibility. `verify` requires full126 and a matching catalogue.

For apply, the operator must separately review the plan and set both `KXRA_PRODUCTION_APPLICATION_PLAN_SHA256` and `KXRA_PRODUCTION_APPLICATION_CONFIRMATION=APPLICATION126:lhbgeucifxxcdoyrnesf:EXACT_SOURCE_COMMIT:EXACT_PLAN_SHA256`. This is an intentional operation-specific confirmation, not a feature flag. It is not consent to spending or a substitute for deployment authorization, backup/restore review or Auth service acceptance. Re-run plan whenever the source, target ledger, schema, role memberships or Auth catalog changes. Do not put credentials in shell history or receipts.

## Safety checks and recovery

The existing `kxra-production-migrations` advisory lock is shared with the117 operator. A competing operator fails promptly. Each migration locks the ledger and Auth sessions, rechecks the exact reviewed plan and source-derived catalogue, executes only the already validated in-memory SQL, records the same name/hash and current exact source commit, and checks the resulting catalogue before committing. A failure rolls back that migration, including DDL and the ledger entry. Earlier committed migrations remain committed. A later invocation requires a new read-only plan and applies only the remaining genuine prefix suffix.

A lost COMMIT acknowledgement stops the invocation with an explicit uncertain-outcome/replan error, including when rollback/unlock also fail on the dead connection. There is no automatic replay. Reconnect and inspect the authoritative ledger through plan; if the transaction committed, that migration is absent from the new pending list. Already126 apply with its current plan is a checked no-op. Manual or other schema writers must be quiesced during approved maintenance; an advisory lock cannot constrain arbitrary superuser activity.

The application catalogue profile is derived from independently installed exact source for every prefix117–126. It includes managed tables, columns, constraints, RLS policies, functions/owners/ACLs, types, sequences, indexes, triggers/enabled state, schemas, rules, relation options and the custom Auth triggers. Only metadata ordering is canonicalized; owners, grants, definitions and security settings are retained. Profiles are keyed by the independently rehearsed PostgreSQL major version. Provider-owned Auth catalogues and PostgreSQL patch versions are not invented as source expectations. A server rendering or ownership difference that changes the managed catalogue fails closed and requires inspection/rehearsal, never a bypass or locally fabricated hosted profile.

Auth checks require a genuine regular `auth.sessions` table owned by `supabase_auth_admin`; UUID session/user keys, session primary key and timestamp dependencies; `auth.uid()`/`auth.jwt()` interfaces; operator SELECT and TRIGGER privileges; required roles without privileged application authority/memberships; no app-accessible Auth table/column privileges; and the precise expected custom trigger set at each prefix. Unexpected Auth session triggers are deliberately unsupported until their ordering and behavior have been reviewed. SQL125/126 themselves install the reviewed custom triggers/functions. The operator does not enable the provider access-token hook or attest to the real provider's insert/refresh transaction timing. Successful catalogue verification is NOT evidence that the hosted Auth service will invoke them in the required original-session ordering.

It never modifies the committed policy. Both modes require a clean exact commit and the shared native lease; owned cleanup is verified before releasing it. Synthetic Auth fixtures are confined to this local verifier, not the production operator.

Before any hosted execution, obtain the authorized target's read-only plan, review the actual existing ledger and any source catalogue differences, confirm backup/restoration and cost controls, verify real Auth sessions/role privileges and insertion/hook ordering for SQL125/126, and complete independent hosted security/customer acceptance.
