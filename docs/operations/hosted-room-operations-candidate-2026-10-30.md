# Existing room jobs and schedules: local hosted candidate

This is an isolated local implementation based on `d2ee06b`, not hosted acceptance or a new agent product. It changes existing queued room drafts and reviewed daily definitions only. Billing freshness scheduling has separate ownership and configuration. No browser, hosted database, deployment, provider activation, real credential creation, role creation, scheduler registration, external send or purchase was performed.

## Implemented boundary

`KXRA_HOSTED_ROOM_JOBS` defaults to false. Admission additionally requires Supabase auth mode and a configured dedicated 64-hex room-worker bearer. Existing fixture guards remain; the fixture launcher is unchanged. The separate `scripts/team-hosted-job-worker.ts --once` submits one opaque delivery UUID to an exact HTTPS origin, with a header bearer and no redirects or browser cookies. It never supplies an actor, organisation, room or grant ID.

The private POST endpoint authenticates before reading a bounded body (256 bytes, eight chunks, two-second body deadline). It accepts only a delivery UUID, processes at most one grant, and returns no identities, source text, provider keys or fencing tokens. Its configured duration is 60 seconds. Existing provider transport has a 25-second deadline and DNS has a five-second bound; the existing job lease is 45 seconds. Lease expiry before completion fences publication. Lost dispatched outcomes retain the existing UNCERTAIN/no-replay rule.

The SQL proposal adds two RLS-protected tables and a separate worker schema containing one discovery function accessible only to the existing NOINHERIT `kxra_app` login. It does not grant that login access to the existing private schema. Public/anonymous/authenticated roles cannot discover grants or invoke worker discovery. Existing RPC `session_user='kxra_app'` checks are retained.

A fresh-MFA authenticated requester authorizes one immutable queued job or reviewed schedule. The persisted grant binds requester, tenant, room, target, application session version, membership version, provider connection identity and a fingerprint of its model/endpoint/encrypted credential configuration. A one-off delegation expires one hour after its due instant; a daily definition uses its selected expiry, bounded to 30 days. Issuing/reviewing and revoking grants writes audit receipts. The grant is not a browser token or API credential.

Every worker database transaction uses the existing authenticated RLS role and a server-resolved principal from the grant. Validation locks the grant row for the transaction, checks current membership/account/session/connection/entitlement/room authority, and serializes against revocation. Claim, schedule tick and pinned-context checks restrict the worker to its exact target and scheduled children. Schedule admission temporarily permits only a child whose pinned inputs exactly match that definition before the occurrence FK can be recorded. The original context/source, quota, retry, cancellation, output and run fences remain in place.

One delivery selects one least-recently-served eligible grant, with a 60-second per-grant delivery cooldown and SKIP LOCKED. A private delivery receipt makes wakeup UUIDs idempotent. Existing actor-level claim serialization still permits only one active lease per requester. A failed delivery is not proof of provider failure and must not be replayed as a new provider dispatch after uncertainty.

Admission suspension does not remove authenticated schedule pause/revoke or job cancellation. Those retain their existing actor/room authorization. UI controls receive a distinct server capability; fixture status is not relabeled as hosted. The readiness report still reports hosted activation/provider acceptance as pending.

## Local verification and invocation

Run the isolated synthetic suite from the checkout:

```sh
KXRA_PG_BIN=/path/to/postgresql/bin node scripts/verify-hosted-room-operations.mjs
```

The harness allocates fresh loopback ports, uses a fresh Unix-socket PostgreSQL cluster, strips inherited cloud/service secrets, generates only its ephemeral fixture session secret, and stops its owned processes. On macOS it sets a stable C locale and uses a short `/tmp` socket path. It applies the SQL proposal only to that fresh fixture, then executes the native operations, existing jobs/schedules and provider protocol suites. It does not use browsers or call a provider. The proposal tests live below `tests/operations` so normal root service discovery does not silently apply an unassigned migration proposal.

Final verification: the combined native operations, existing jobs/schedules and provider protocol invocation passed **20/20**, zero skips. A subsequent fresh operations-only invocation passed **4/4**, including the final scoped grant-row lock and fresh-MFA negative checks. The OS production build passed and includes the internal worker route. The final boundary refinement passed **3/3**, including stop lock order and server-resolved discovery/rollback. Root typechecking, changed-file formatting and the 923-file publication/secret scan passed. Initial harness startup failures and a corrected fixture cleanup failure are retained in local `/tmp/room-tests*` logs; none is reported as acceptance. The final receipts are `/tmp/room-tests-acceptance.log`, `/tmp/room-operations-final-native.log`, `/tmp/room-operations-build.log` and `/tmp/room-operations-types-final.log`.

Native operations coverage includes actual `kxra_app` discovery permissions, unauthorized requester/tenant rejection, cross-target isolation, concurrent discovery and claims, delivery replay, grant expiry and application session-version withdrawal. Additional native coverage exercises a second requester and a reviewed daily definition spawning/finishing its permitted child without replaying publication. The existing jobs/schedules suites exercise retry exhaustion, pre/post-dispatch crash semantics, cancellation, late completion, source/membership/tenant withdrawal, DST gaps/folds, overlap, daily budgets and histories larger than 100 rows. Pure endpoint tests verify disabled admission, stop controls, strict wakeup scope and body bounds.

## Integration and approval still required

1. Review the exact commit and `proposals/hosted-room-operations.sql`. Release must assign the next migration number in coordination with billing and security, preserve the existing 112-migration manifest, and update the exact staging/production inventory plans. This proposal is deliberately outside the frozen migration sequence; merely deploying this source does not install the schema. No Supabase CLI is installed in this environment, and no hosted migration was attempted.
2. Review the two-line removal in shared `team-workspace.ts`, the additive internal principal/transaction handling in `packages/db/index.ts`, the capability prop in the OS page, and the related UI changes together. Auth routes were not changed. Integrate the shared file by reviewed diff rather than overwriting another task's edits. Aggregate CI, CodeQL and independent security/QA acceptance remain release gates. QA baseline contract `aa26420` must mock the new capability helper and replace its blanket review-503 assertion with ACTIVATE rejection plus PAUSE/REVOKE availability; that behavior change is deliberate. The candidate includes those boundary checks locally.
3. Approve a dedicated room wakeup credential and its custody, the exact target deployment, and a scheduler using existing approved infrastructure. Do not reuse billing secrets, auth/session tokens, a service-role key or administrator database credentials. A scheduler must POST to `/api/internal/room-jobs/drain` with the dedicated bearer and a fresh UUID. The CLI is a bounded process option, not an installed service. Protected-deployment delivery and its authentication must be verified with the actual approved host.
4. Set the application flag only after the schema, secret and delivery path are verified. Approve bounded provider acceptance separately, including the selected existing connection, model, run/token limits and spend ceiling. No configured key is accepted as evidence of a successful real provider run.
5. Confirm hosted timezone data for supported zones before daily-schedule acceptance. The [30 October Supabase changelog](https://supabase.com/changelog) identifies a current timezone-data correction for Vancouver, Edmonton and Casablanca; no upgrade was attempted here. Prove the final hosted flow across two actual tenant/requester scopes, including private nonmembership, membership/connection/payment withdrawal, timeouts/429s, worker crashes and late publication. Native synthetic and protocol tests cannot establish provider-network delivery, actual protection settings, external session-revocation semantics or launch readiness.
6. Choose cadence/capacity and monitoring before activation. One wakeup handles at most one grant; at one wakeup/minute the ceiling is one selected scope/minute, with least-recently-served traversal, not an unlimited drain. Use delivery receipts, audited grants, attempts/states and platform status/error/latency counters. Set a no-progress/UNCERTAIN alert and retention policy for delivery receipts. Grants whose authority expires or is withdrawn stop executing; existing requester drains/stop controls reconcile their pending state. A separate operator-only reconciliation/retention policy is still needed for abandoned expired scopes.

To suspend, set the admission flag false and stop scheduled wakeups; authenticated pause/revoke/cancel remains available. Revoke affected definitions/jobs through the existing scoped controls. Already received provider work cannot be recalled, but stale output is fenced. Public offers must continue to exclude unattended/recurring execution until the preceding acceptance is complete.
