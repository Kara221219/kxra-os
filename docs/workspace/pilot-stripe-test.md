## Prerequisites and routes

A reviewed operator must provision the **empty** pilot_stripe_config singleton with existing test account, monthly price/product, optional setup price/product, restricted portal configuration and a specific terms-review reference/tax decision. No row is seeded, no browser/LLM value chooses these fields and the offer remains £49/month/workspace/five people/customer-paid AI, optional £199 onboarding. A test price must match4900GBP/month/one licensed quantity, or19900GBP/one-time setup, active test product and the reviewed tax behavior. Choosing tax behavior in a synthetic protocol test does not approve real VAT terms.

`KXRA_PILOT_STRIPE_ENABLED` defaultsfalse. The server additionally requires a test-only key, exact hosted HTTPS origin, separately scoped webhook secret and existing billing-worker database identity. Only a fresh MFA current tenant owner can request `/api/team-space/pilot/billing/{checkout,portal,reconcile}` with a UUID request_id (checkout optionally includes include_setup). Caller price/customer/tenant/role/entitlement fields are rejected. Existing verified billing_customers must already map this workspace; this slice does not bootstrap accounts. Before a provider POST, the adapter retrieves and checks the account, test price/product and customer. Portal configurations require cancellation enabled and subscription product/price updates disabled. No tax/refund/cancel policy is silently published.

One durable checkout intent per workspace prevents duplicate subscriptions after lost responses. Retry the original request UUID and exact payload within23hours; later uncertainty needs operator reconciliation, not a second automatic checkout. Provider POSTs use stable `kxra-pilot-<intent>` idempotency. Ready sessions return only validated Stripe HTTPS URLs, exact customer and bounded expiry. The return URL grants no access. Existing fixture pilots cannot switch to provider mode. Resubscription after a bound terminal subscription is intentionally unavailable pending a reviewed policy.

## Events and entitlement authority

The isolated `/api/webhooks/workspace-pilot` verifies the bounded raw body and Stripe signature against the separate secret, rejects live/malformed snapshots and accepts only the pinned subscription event family. It requires a single licensed GBP4900/month line, exact reviewed product/price/tax, test flags, current customer binding and subscription metadata pointing to a pre-existing checkout intent. Metadata never chooses a tenant; the database resolves the customer to its current immutable workspace binding. Provider snapshots do not create users, memberships or access grants.

The existing nonlogin, non-bypass billing-worker role has only narrow receipt RPCs, no table access. A transaction serializes on the same workspace lock as seat/work/publication admission. Exact event-ID/hash replay returns its existing outcome; changed bytes conflict. Older events are recorded STALE. Conflicting states with equal provider timestamps suspend access and mark RECONCILE_REQUIRED; newer webhook delivery alone cannot clear the uncertainty. A fresh owner reconciliation intent captures the current binding version, retrieves the actual subscription through the validated test transport and applies only if no intervening event changed that version. Completed reconciliation request retries do not fetch/reapply a different snapshot. Cancelled subscriptions remain terminal; an old active event or contradictory reconciliation cannot resurrect one.

Only accepted provider state updates opt-in TEST_STRIPE workspace_pilots. ACTIVE requires current period, active status and at most five reserved real memberships/invitations. Trial/incomplete/past-due/paused/expired states do not grant work. Existing five-person reservation, cancellation/expiry, history-read and late-output gates remain. Event storage failures return503 for provider retry; signature failures return400; unsupported signed events are ignored. A failed/unknown mapping grants nothing and can be retried after operator repair.

## Protocol references

The implementation uses raw-body verification and version-pinned snapshot contracts from [Stripe webhooks](https://docs.stripe.com/webhooks), [Checkout creation](https://docs.stripe.com/api/checkout/sessions/create), [Price objects](https://docs.stripe.com/api/prices/object), [portal sessions](https://docs.stripe.com/api/customer_portal/sessions/object) and [portal configuration](https://docs.stripe.com/api/customer_portal/configurations/object). These references document provider behavior; they are not evidence that KXRA has connected a Stripe account.

Signed invalid-offer updates for an already bound subscription now have a **denial-only quarantine** path: exact signature/customer/subscription provenance is required; invalid price/quantity/product data can pause new work, never grant it. Unknown bindings fail for retry. Older invalid snapshots are stale, conflicting current snapshots require owner reconciliation, and signed deletion can mark a known subscription terminal even when its offer snapshot is invalid. Event bytes remain immutable/idempotent. Current billing_customer mapping is rechecked on every provider entitlement/admission; remapping cannot leave the old subscription granting access. Five-person holds start with the explicit pending checkout binding, before its first provider event; the same lock serializes first assignment and invitations.
