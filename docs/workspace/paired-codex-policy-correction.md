## Documented controls and source changes

Current [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) retires `approval_policy="untrusted"`. The protocol now requests documented **on-request** approval at thread and turn creation. It never approves a request: any peer tool/permission request terminates the cycle. Approval mode is distinct from tool availability and filesystem/network policy.

`codex-text-policy.ts` defines an immutable explicit configuration: command tools/snapshots, apps, hooks, multi-agent tools, image viewing, remote plugin catalogue, skill dependency installation, goals and memories are off; web search is disabled; app/plugin defaults are disabled. The MCP configuration is empty and an empty, fully paginated runtime MCP catalogue is required. There is no invented global MCP wildcard-disable switch. The documented per-server controls remain `enabled`, `enabled_tools` and `disabled_tools`; this slice instead accepts no server at all. A default plugin disable cannot override managed enablement, and these settings are **not** proof that an arbitrary installed CLI has zero executable tools.

Each injected stub process receives an owned fresh `/tmp/kxra-codex-*` HOME, CODEX_HOME and working directory. Only fixed PATH/NODE_ENV accompany them. A mode0600 config.toml and matching fixed `-c` overrides contain public settings only; no credential is read/copied/created. Legacy operator HOME/cwd fields remain validated for interface compatibility but cannot select the process environment or working directory. Project instruction bytes are zero; authentication storage is configured ephemeral and history persistence none. These settings do not prove that all real CLI histories/state are absent. [Config locations and precedence](https://learn.chatgpt.com/docs/config-file/config-basic), [CODEX_HOME](https://learn.chatgpt.com/docs/config-file/environment-variables), [credential storage](https://learn.chatgpt.com/docs/auth).

**No real installed version is accepted.** The supervisor constructor without an injected fixture launcher and foreground `--codex-stdio` both refuse with `CODEX_INSTALLED_ACCEPTANCE_REQUIRED` before starting a CLI, creating config or redeeming a pairing invitation. The base protocol requires a synthetic channel. The sole handshake identity is the checked-in `kxra-codex-policy-stub/1`; it is not a real version, signed binary identity or security attestation. An injected launcher is a trusted test seam, not an HTTP/model-controlled activation flag.

The [App Server interface](https://learn.chatgpt.com/docs/app-server) documents config/read, configRequirements/read and MCP status inspection. Before thread/turn dispatch the narrow stub contract requires: exact known identity; null managed requirements; exact configuration without unknown enabled/missing settings or accepted external origins; and empty MCP data with no next cursor. Unknown methods, versions, capability fields, requirements, response shapes or acknowledgements refuse; there is no compatibility fallback. These RPC names are documented, but the exact minimal response profile has been verified only against the checked-in peer. Installed schemas/effective config and startup behavior still need separate acceptance.

Frames are bounded and structurally checked. Responses must be one result or error for a pending numeric ID. Peer requests, unknown notifications, tool items and invalid shapes are rejected on receipt. During thread creation only a strict thread-started notification can queue; its identity is checked against the thread acknowledgment before sources are sent. This closes the review finding where a forbidden early notification could otherwise be discovered after turn/start. Sources, approval hashes, tenant/session/task/fence binding, no-replay semantics and original-room draft publication are unchanged.
