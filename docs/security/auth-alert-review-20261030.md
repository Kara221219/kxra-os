## Alerts 1 and 2: password-hash rule

Alert 1 points to the local password-reset email operation key in `apps/os/app/api/password-reset/route.ts`. Its SHA-256 input is `issued.token`, generated by the fixture provider from 32 random bytes. The truncated digest is an email-operation idempotency component, combined with the fixture identity ID; it is not the password verifier or the recovery-token verifier. The raw recovery token is not replaced by that operation key. This branch requires the guarded local fixture mode.

Alert 2 points to `digest()` in `packages/authz/fake-provider.ts`. Its callers digest random email-verification and password-reset tokens for comparison. Actual fixture passwords use a fresh salt and scrypt, and password verification compares the derived buffers with `timingSafeEqual`. Hosted password verification/update is delegated to Supabase rather than this fixture file. SHA-256 for a high-entropy random token is a different use from hashing a user-chosen password; replacing these token digests with a password KDF is not a justified repair for the reported rule alone.

The same route also hashes a normalized email into a rate-limit key. That input is predictable and must not be described as a random secret or as password storage. The source review makes no claim of identity confidentiality if that rate-limit index is exposed.

Proposed disposition: retain the findings pending independent security review and exact integrated-source analysis; document their non-password inputs and guarded fixture boundary. No suppression, dismissal or security-rule change is included.
