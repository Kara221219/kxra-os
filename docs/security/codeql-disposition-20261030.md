# Token-digest and file/network finding disposition

This supplement reviews the 11 remaining token/dataflow alerts against local base `d5e16ba`, filesystem/download hardening `b21dd40`, current read-only GitHub source/sink messages, and QA's independent retained notes at `task-3/codeql-review-to-security-owner.md`. No remote alert disposition, suppression, rule change, publication or provider operation occurred. The local follow-up changes only two manual operator scripts, a new polling helper, a new standalone evidence test, and documentation. Auth/recovery and billing implementation files remain untouched.

“False positive” below means the reported security weakness is unsupported at the inspected sink; the underlying dataflow can still be real and intentional. “True positive, locally mitigated” identifies an original unsafe boundary with source/test mitigation, without claiming a remote closure. “Unresolved” requires the stated evidence before that workflow is accepted. GitHub's [file-to-HTTP rule](https://codeql.github.com/codeql-query-help/javascript/js-file-access-to-http/) concerns unintended disclosure; its [HTTP-to-file rule](https://codeql.github.com/codeql-query-help/javascript/js-http-to-file-access/) also flags deliberate downloads and asks reviewers to assess their purpose. Fixed filenames alone do not settle content trust.

## Evidence tests and practical limits

`tests/codeql-disposition.test.ts` dynamically confirms salted scrypt rather than SHA-256 password storage, distinct salts/hashes for equal synthetic passwords,32-byte verification/reset tokens, digest-only persistence, old-token rotation rejection, expiry, and one successful reset when two calls use the same fixture-provider instance. It does not establish hosted Supabase nonce/TOTP reuse, cross-process atomicity, access-token invalidation, or production account recovery.

The polling tests use an injected in-memory transport and synthetic credentials. They assert the exact fixed origin/path and absence of a request body, redirect rejection, ID/path/query/destination rejection before transport, mismatched job rejection, bounded metadata, overflow cancellation and sanitized JSON-parser errors. They never invoke a billable SDK call or a real endpoint. New helper behavior is exercised by both scripts; malformed saved IDs fail closed without submission.

The installed SDK's initial submission still uses its own Axios client. This follow-up does not establish a response-size or redirect policy for that separate SDK path. No SDK/dependency code was changed. Before any separately authorized new generation, review that client policy and the private ledger, approved run identity and current budget; never resubmit uncertain prior work. Those conditions concern excluded manual tooling, not evidence of customer-runtime exposure.
